This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

## Stack

Next.js 16 (App Router, `src/` dir, Turbopack) · React 19 · TypeScript · Tailwind CSS v4 · Better Auth · Drizzle ORM · Postgres on Neon. Path alias `@/*` → `src/*`.

Next.js 16 differs from older versions (e.g. `middleware` is now `proxy`). Check `node_modules/next/dist/docs/` before writing Next-specific code.

## Commands

Package manager is **pnpm** only (`pnpm-lock.yaml`). Node version is pinned in `.node-version` (managed with fnm).

```bash
pnpm dev            # dev server on :3000
pnpm build          # production build
pnpm lint           # eslint
pnpm typecheck      # tsc --noEmit
pnpm test           # vitest run (unit tests: src/**/*.test.ts)

pnpm db:generate    # drizzle-kit: create SQL migration from schema changes → ./drizzle
pnpm db:migrate     # apply migrations to DATABASE_URL
pnpm db:push        # push schema directly (prototyping only)
pnpm db:studio      # Drizzle Studio
pnpm db:seed        # idempotent catalog seed (tsx, src/db/seed.ts)

pnpm auth:generate      # Better Auth CLI (`auth@1.7.7` via pnpm dlx) → writes src/db/schema/auth.ts
pnpm auth:create-admin  # create an admin user (--email, --name; prompts for the password)
scripts/auth-smoke.sh   # curl smoke test of the auth flows against a running dev server
```

Vitest (`vitest.config.mts`, node environment, `@/` alias) covers pure logic only; there are no component or e2e tests yet.

Env vars live in `.env.local` or `.env` (template: `.env.example`): `DATABASE_URL` (Neon pooled URL), `BETTER_AUTH_SECRET` (32+ chars, `openssl rand -base64 32`; without it Better Auth signs cookies with a public default and production throws), `BETTER_AUTH_URL` (also the base of Stripe's success/cancel URLs), `STRIPE_SECRET_KEY` (a restricted `rk_` key with Checkout Sessions write), `STRIPE_WEBHOOK_SECRET` (`whsec_…`, from `stripe listen` locally) and `CRON_SECRET` (bearer token for the order sweeper). Next loads both natively; `drizzle.config.ts` (dotenv) and `db:seed` (`--env-file-if-exists`) load both too, with `.env.local` taking precedence.

## Architecture

- **DB client** — `src/db/index.ts` exports `db`, a Drizzle client over Neon's HTTP driver (`drizzle-orm/neon-http`). It is stateless per query, so it has no interactive transactions; switch to the `neon-serverless` (WebSocket) driver if those are needed.
- **Schema** — `src/db/schema/index.ts` is the barrel that both `db` (typed relational queries) and drizzle-kit (`schema: "./src/db/schema"`) read. Every new table file must be re-exported from it.
- **Auth server** — `src/lib/auth.ts` exports `auth`, built on the Drizzle adapter (`provider: "pg"`) and the shared `db`. Email & password only (no email verification, reset or social login yet). Sign-up asks only for email and password; Better Auth requires `name`, so it's stored as `""`. Treat `user.name` as optional in the UI. Sessions last 30 days, slide once a day, and use a 5-minute cookie cache. The `admin` plugin adds `user.role` (`"user"` | `"admin"`), which sign-up can't set. `nextCookies()` must remain the **last** plugin. The CLI is the `auth` package pinned to the installed `better-auth` version (`@better-auth/cli` is deprecated and stuck on 1.4).
- **Auth tables** — Better Auth's tables are generated, not handwritten. After changing auth config or plugins, run `pnpm auth:generate`, then `pnpm db:generate && pnpm db:migrate`. `src/db/schema/auth.ts` is re-exported from the schema barrel; don't edit it by hand.
- **Auth HTTP** — `src/app/api/auth/[...all]/route.ts` mounts the handler with `toNextJsHandler(auth)`. Sign-in and sign-up forms (`src/components/auth/auth-form.tsx`) call `authClient` (`src/lib/auth-client.ts`) so requests go through that handler: Better Auth's rate limiter and origin check only run on HTTP requests, so don't move credential checks into server actions that call `auth.api.signInEmail()` directly. Sign-out is a server action (`src/app/(auth)/actions.ts`).
- **Sessions on the server** — read the session only through `src/lib/session.ts` (`server-only`): `getSession()`, `requireSession(returnTo)` (redirects to `/sign-in?next=`), `requireFreshSession(returnTo)` (like `requireSession` but bypasses the 5-minute cookie cache, so revoked sessions are refused at once; used by the order pages, which show addresses), `requireAdmin()` (bypasses the cookie cache; non-admins get a 404) and `safeNext()` (same-origin redirect targets only). Every protected page **and** server action must call one of these itself. Layout checks alone aren't enough.
- **Proxy** — `src/proxy.ts` matches `/account/*` and `/admin/*` and only redirects when there's no session cookie (`getSessionCookie`). It does not validate the cookie and isn't a security boundary.
- **Keep catalog pages static** — don't read the session (or `headers()`/cookies) in the root layout, `SiteHeader` or catalog pages; that would make every ISR page dynamic. RSCs can't write cookies, so protected pages render `SessionKeepAlive`, which calls `/api/auth/get-session` to slide the session expiry.
- **Auth routes** — `/sign-in` and `/sign-up` (`src/app/(auth)/`, `?next=` return path), `/account` (customer) and `/admin` (admin placeholder). All are dynamic and `noindex`.
- **Account area** — `src/app/account/layout.tsx` renders the shared shell (`AccountBreadcrumbs`, `AccountNav` and `SessionKeepAlive`) and doesn't read the session. Sections are `/account` (overview), `/account/orders` (order history) and `/account/details` (`ProfileForm` updates the name and `PasswordForm` changes the password and revokes other sessions, both through `authClient`). To add a section, add it to `ACCOUNT_LINKS` in `src/components/account/account-nav.tsx`. Order history lists only orders whose `user_id` is the signed-in account (`getCustomerOrders`, never matched by email) and only completed checkouts (`CUSTOMER_ORDER_STATUSES`: paid, processing, needs_review, failed). `/account/orders/[id]` loads through `getCustomerOrder(userId, id)`, which puts ownership in the query and selects only the fields shown. Anyone else's order, an unfinished checkout and an unknown id all render the same `not-found.tsx` (404, inside the account shell), so ids can't be probed. Orders link to an account only if the customer was signed in at checkout. Shared UI is in `src/components/orders/` (`OrderStatus`, `OrderSummary`, also used by the confirmation page). There's no `loading.tsx`, because a Suspense boundary would turn `requireSession`'s 307 into a streamed redirect.

## Design system

Tailwind v4, CSS-first (no `tailwind.config`). `src/app/globals.css` only imports:
- `src/styles/theme.css`: `@theme` tokens. The default colors, type scale, radii, tracking and breakpoints are **reset**, so stock classes like `text-gray-500`, `rounded-lg` or `2xl:` don't exist. Use the semantic tokens (`bg-bg-muted`, `text-fg-muted`, `border-border-strong`, `aspect-product`, `ease-editorial`). Breakpoints: `sm` 480, `md` 768, `lg` 1024, `xl` 1440.
- `src/styles/base.css`: per-breakpoint runtime vars (`--gutter`, `--header-height`, `--section-space`, exposed as `px-gutter`, `h-header`, `py-section`) and element defaults.
- `src/styles/primitives.css`: `@utility` primitives for layout (`page-container`, `grid-12`, `product-grid`), media (`media-frame`, `media-product`), type roles (`type-*`), buttons (`btn` + `btn-primary|secondary|inverse|ghost`, `btn-icon`), links (`link`, `link-quiet`) and forms (`field`). Prefer these over ad-hoc utility stacks.

Visual rules: the UI is monochrome (imagery supplies the color) and light-only. Corners are square (radius only on `xs` inputs and round icon buttons), borders are 1px hairlines, and text labels are 12px. Fonts come from `next/font` in `layout.tsx`: Hanken Grotesk (`--font-hanken` → `font-sans`) and EB Garamond (`--font-garamond` → `font-serif`, wordmark only).

## Storefront

- **Catalog** — products, categories and product images live in Postgres (`src/db/schema/catalog.ts`). Stock is the `products.stock` column (no variants yet), prices are integer cents, and image `position` 0 is the card shot. `products.gender` (`women` | `men` | `unisex`) is separate from the product-type category; unisex pieces appear on both `/shop/women` and `/shop/men`. Read products only through `src/lib/catalog.ts` (`getProduct`, `getProductSlugs`, `getNewArrivals`, `getProductsBySlugs`, `getRelatedProducts`, `getCategory`, `getCategorySlugs`, `getProductsByCategory`, `getProductsByGender`, `searchProducts`), which maps rows to the `Product` view type. Seed data is in `src/db/seed-data.ts`.
- `src/lib/sample-data.ts` holds editorial content only (hero, category tiles, collections, nav, footer). The featured collection references products by `productSlugs`. Photos come from `images.unsplash.com` (allowed in `next.config.ts` under `/photo-*` only); URL helpers are in `src/lib/unsplash.ts`.
- Pages that read the catalog use `export const revalidate = 60` (ISR). `pnpm build` needs `DATABASE_URL` pointing at a migrated, seeded database.
- `SiteHeader` and `SiteFooter` are rendered from the root layout. The header is transparent only on routes in `OVERLAY_ROUTES` (pages that open on a full-bleed image). Other pages must add `pt-header` themselves so content isn't hidden under the fixed header.
- Homepage sections live in `src/components/home/`. Product UI (`ProductCard`, `ProductGallery`, `ProductInfo`, `StockStatus`, `Disclosure`) lives in `src/components/product/`.
- Listing pages live under `src/app/shop/`: `new` (newest products), `women` and `men` (both via `gender-page.tsx`), and `[category]` (product-type slug, statically generated from `getCategorySlugs()`, 404 for unknown slugs). They all render `ProductListing` (`src/components/product/product-listing.tsx`). Static routes take precedence over `[category]`, so a category can't use the slugs `new`, `women` or `men`.
- Collection pages are `src/app/collections/[slug]/page.tsx`: editorial collections listed in `collectionPages` (`sample-data.ts`), rendered with `ProductListing` from their `productSlugs` in order. Other slugs 404 (`dynamicParams = false`). The homepage `FeaturedCollection` previews only the first four slugs.
- Search is `src/app/search/page.tsx` (`/search?q=`, dynamic, `noindex`). `searchProducts()` is Postgres full-text search: `products.search_vector` is a generated, GIN-indexed `tsvector` (name A, color B, description C, `simple` config), and categories are matched by name in the same query. `searchTerms()` is the single place a raw query becomes searched words (first 100 chars, NFC, runs of letters/marks/decimal digits, 2+ chars, max 6; case is left to Postgres). Each word is a prefix match on word starts and all must match; names matching the most words rank first. `searchProducts(query, offset)` returns one page (`SEARCH_PAGE_SIZE`) of `ProductSummary` (card fields only, so search never ships descriptions or galleries to the client), the total and the terms. The page server-renders the first page; `SearchResultsGrid` (client) appends further pages from the `GET /api/search?q=&offset=` Route Handler (offset capped at `MAX_SEARCH_OFFSET`) on "Show more". It pages by rows received, duplicates included, so a catalog change between clicks can skip new products but never stalls, and moves focus to the first new card (or the status line). Inside `db.query` `where` SQL, every column is remapped to the root table alias, so subqueries on other tables must be `db.select()` builders. `SearchForm` (`src/components/search/`) is a `next/form` GET form, so it works without JS; with JS it debounces `router.replace` as you type. An empty query shows new arrivals.
- Shared listing UI: `Breadcrumbs` (`src/components/breadcrumbs.tsx`) and `ProductGrid` / `ProductGridSkeleton` (`src/components/product/product-grid.tsx`).
- Loading states are page skeletons built from `Skeleton` (`src/components/skeleton.tsx`): `src/app/shop/loading.tsx` (every `/shop` listing) and `src/app/collections/loading.tsx` (collection pages) both render `ProductListingSkeleton`, and `src/app/products/[slug]/loading.tsx` covers the product page. When a page's layout changes, update its skeleton to match so the content doesn't jump when it loads.
- The product detail page is `src/app/products/[slug]/page.tsx`, statically generated from `getProductSlugs()`. Stock states come from `getStockState()` in `src/lib/stock.ts`: 0 is out of stock, 3 or fewer is low stock. Use that function rather than comparing `stock` inline.
- Gallery images beyond the first are `detail()` crops: 3:4 focal-point zooms of the primary Unsplash photo. Check crops visually; zooms can expose brand labels.
- **Shopping bag** — `/bag` (`src/app/bag/`, dynamic, `noindex`). The bag is a `bag` cookie of `[slug, quantity]` pairs (`src/lib/bag-cookie.ts`: parse/serialize, max 50 lines, quantity 1–99). It never stores prices or stock, and it isn't `httpOnly` so the static header can show the count (`useBagCount`, `src/components/bag/use-bag-count.ts`). Only `/bag` and the server actions in `src/app/bag/actions.ts` (`addToBag`, `updateBagQuantity`; quantity 0 removes) read the cookie, through `src/lib/bag.ts` (`server-only`), so catalog pages stay static. Actions check fresh stock with `getAvailableStock()` (`src/lib/bag.ts`: uncached `getStockBySlugs()` plus units the visitor's own pending checkout holds; ISR pages can be a minute stale), apply the pure rules in `src/lib/bag-reconcile.ts` (`applyAdd`, `applyUpdate`, `normalizeBag`, `reconcile`), write the whole bag back normalized, and the client calls `notifyBagChange()` so the header updates. The page prices lines from current rows and clamps to stock at render. RSCs can't write cookies, so when the page clamped or dropped lines it renders `BagSync`, which POSTs `/api/bag/sync` to save the corrections (a Route Handler, not an action, so the page doesn't re-render and lose its notices); without JS the next action does it. Sold-out lines stay visible but don't count toward the subtotal; the summary lists them separately. Actions return an error state instead of throwing when the stock lookup fails. A removed line unmounts with its own status message, so removals are announced through the page-level `BagAnnouncer` (`announceBag()`). The bag itself is guest-only (no account sync); stock is reserved only once checkout starts (see Checkout).
- **Checkout** — Stripe Checkout (hosted page, `mode: "payment"`). Our database owns products, prices, stock and orders; Stripe owns payment collection, payment methods, email/shipping-address collection and receipts. There's no Stripe catalog: line items are inline `price_data` built from the order's rows. Tax isn't enabled (no `automatic_tax` until there's a Stripe Tax registration).
  - `startCheckout` (`src/app/checkout/actions.ts`, form `CheckoutForm` in `BagSummary`) re-reads the bag with `getCheckoutProducts()` (uncached) and `reconcile()`, and sends the customer back to `/bag?notice=changed` if the subtotal or count differs from what the page posted. Those values only detect changes and are never charged. It then calls `createPendingOrder()`, which inserts the order and its items and decrements stock in one `db.batch()` transaction. The `products_stock_nonnegative` check rejects oversells (`OutOfStockError` → `/bag?notice=stock`). Only then does it create the session (idempotency key `checkout:<order id>`, `expires_at` 31 minutes out, `metadata.order_id`) and redirect. If the Stripe call fails, the order is `canceled` and its stock returned. An `httpOnly` `checkout_order` cookie lets the next checkout release the previous pending one (`abandonCheckout`), so one visitor never holds stock twice. Units held by the visitor's own pending order count as available to them (`getAvailableStock()` / `getBag()` in `src/lib/bag.ts`), so going back from Stripe never shows their pieces as sold out. Stripe's `cancel_url` is `GET /checkout/cancel`, which releases the hold immediately and redirects to `/bag?notice=canceled`.
  - Orders (`src/db/schema/orders.ts`) are written only through `src/lib/orders.ts`. Status changes go through `transition()`, which applies only from the statuses in `ORDER_TRANSITIONS` (`src/lib/checkout-rules.ts`). Restocking transitions (`expire`, `fail`, `cancel`) return the units in the same SQL statement, guarded by `stock_released`. That makes replayed and out-of-order events no-ops; keep it that way.
  - Payment is confirmed only from Stripe objects. `POST /api/stripe/webhook` verifies the signature on the raw body, dedupes on `stripe_events`, and handles `checkout.session.completed` / `async_payment_succeeded` (`fulfillFromSession`: `paid`, `processing` for delayed methods, or `needs_review` if the amount or currency differs from the order), `async_payment_failed` → `failed` and `expired` → `expired`. The webhook is the only writer: `/checkout/success?session_id=` only reads the order (`getOrderBySessionId`) as the webhook confirmed it, and the query param is only a lookup key. It renders a view per order status (`VIEWS`), and lists the order items while the order is pending and once it's placed. While the order is still `pending`, the page shows "Confirming your payment" and `OrderStatusPoller` (`src/components/checkout/`) polls the read-only `GET /api/orders/status?session_id=` every 2 s. When the status changes it calls `router.refresh()`. After about a minute it stops and offers "Check again". Without JS, a `<noscript>` link reloads the page. The page shows no email or address, and once the order is paid, processing or under review it clears the bag through `BagClear` → `POST /api/bag/clear`.
  - `GET /api/cron/expire-orders` (`Authorization: Bearer $CRON_SECRET`, run every ~15 minutes) settles pending orders 10+ minutes past expiry whose webhook never came.
  - Local testing: `stripe listen --forward-to localhost:3000/api/stripe/webhook`. Use a Stripe sandbox, not the shared test mode.
- next/image in Next 16: use `preload` for above-the-fold images (`priority` is deprecated). The default `qualities` is `[75]`.

## pnpm build scripts

`pnpm-workspace.yaml` → `allowBuilds` whitelists esbuild (needed by drizzle-kit). It explicitly denies `@prisma/client` and `better-sqlite3`, which pnpm auto-installs as optional peers of better-auth and this project doesn't use. New packages with install scripts will fail `pnpm install` until they're added there.
